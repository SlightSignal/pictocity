## 0.2.2 canvas image consistency

Historical implementation version: 0.2.2. Its installation and exact package/API/native acceptance are recorded in the private historical release archive. The 0.2.1 section below preserves evidence for those historical bytes, including its red-canvas/blue-export limitation. Both editors and all original project libraries remain in scope; creative quality and competitor parity require separate evidence.

The editor now tracks referenced image content by preflight SHA-256 as well as source and active document scope. A single asset lifecycle subscriber in `store.ts` covers snapshots, local operations, undo and redo. Socket open/message handlers and history responses from obsolete document connections are ignored; switching documents clears the former document immediately. The new `asset-refresh.ts` controller coalesces overlapping checks, debounces automatic boundaries by 250 ms, loads changed images sequentially and bounds the complete check/load operation to 30 seconds. Hiding, disconnecting, unmounting, changing references or switching documents cancels obsolete work. Late image decodes are discarded and disposed.

Refresh occurs on canvas mount/reconnection, changed asset references, return to visible/focused state, the explicit **Refresh images** button, and export checks. No asset polling or per-frame resource hashing is added. External changes made while continuously focused are detected at the next refresh boundary; this is not a live filesystem watcher. A failed check, unavailable resource or failed image decode leaves no ready image value and reports a visible issue. Missing image layers use the core's existing placeholder. While checks run, the canvas reports that its image sources are being checked.

`env.ts` loads blob images through the authenticated read-only `/api/docs/:id/asset-content?assetId=...&sha256=...&expectedRev=...` endpoint. It streams at most 64 MiB, verifies the requested digest against the actual returned bytes, rejects obsolete revisions/content with 409 and missing/unreadable sources with 422, and serves successful bytes with `no-store`. It resolves the existing local asset aliases through `assetFile`, admits at most two simultaneous responses, and retains its quota until the file read settles and the response finishes/closes. A 30-second server deadline aborts stalled reads and closes unfinished responses; a request that times out before headers returns 408. Client cancellation is linked to the API abort context. The endpoint neither writes assets nor creates resource snapshots. Rechecking the digest when serving closes the preflight-to-image-load race.

Identity, readiness and availability changes clear the editor's image-dependent raster cache and advance an asset version. `CanvasView` also drops its composite and hit-test rasters immediately, fences queued animation-frame work to the current document, and clears its alpha hook on unmount. The core render keys and document asset records/revisions are unchanged. This covers image layers, group composites, raster masks and patterns through full raster-cache invalidation. Pattern-fill layers now enter the shared resource reference set, so preflight, immutable captures and exports consume their actual image bytes.

`ExportDialog` shares the refresh/preflight result, accepts only its current document/revision, and retains first-file and later-file `expectedResources`/`expectedRev` guards. Preview URLs now carry both guards and unavailable previews are reported. Obsolete export responses cannot trigger downloads or update a newly selected document. Export progress queries remain separate from asset refresh: one at a time, 500 ms after completion, with a five-second request timeout; they stop while hidden/disconnected or after unmount. Existing snapshot capture, revision checking, guarded publication and resource cleanup code is preserved.

## Resource integrity

The preflight API `/api/docs/:id/preflight` and MCP `preflight_document` return the checked revision, image digests, required fonts and specific failures. Checks include images, raster masks, enabled patterns, hidden layers and character font runs. Missing or invalid resources refuse rendering with HTTP 422. Unused image records do not block raster rendering. Available fallback stacks and generic CSS families are allowed; availability does not prove style selection, glyph coverage or typography equality.

Asset files must resolve inside the local library. Existing `assets/filename`, `/assets/filename` and basename references resolve to the same local bytes without rewriting documents; nested paths, remote URLs and traversal refuse. Image caches use content SHA-256 rather than timestamps, so same-size replacements with unchanged timestamps cannot return stale pixels. Sequential decoding avoids concurrent image allocations. Limits are 128 MiB retained cache, 256 MiB project decoded working images, 64 MiB compressed source, and 16384-pixel side / 64 MP decoded images. Decoded limits are checked after native decoding; they do not guarantee pre-decode protection from compressed image bombs.

Image uploads validate before atomic publication. Invalid fonts cannot replace existing files; different bytes with a colliding filename refuse with 409. Fonts persist across extraction and restart. Portable imports allocate new image filenames to protect other projects. Package export refuses missing resources rather than silently omitting them. Font files are not embedded in project packages; carry licensed fonts separately.

## Isolated exports

Exports accept `expectedRev`; stale requests refuse with 409. The document is copied before rendering and again before queueing. Later edits cannot alter queued document snapshots. In 0.2.0, image/font bytes were read when rendering started. The 0.2.1 source batch closes that gap with private resource copies before queueing, as described above.

Each render uses a separate Node process. One task runs and four may queue; saturation refuses with 429. The Open dialog schedules thumbnails in groups of three. Documents have a 16 MiB render snapshot budget and encoded output a 256 MiB IPC publication budget. Disconnect cancels queued work immediately and active work cooperatively. A watchdog and kill fallback bound stuck tasks. A failed renderer refuses its task and leaves subsequent work usable. Encoded results and IPC copies still consume memory; full file streaming remains future work.

Video streams raw frames to FFmpeg with backpressure, bounded errors, cancellation and timeout cleanup. Dimensions pad upward without cropping or stretching, including fractional scales. Short audio pads to the picture duration. Video transparency and per-artboard video refuse explicitly. GIF uses bounded global palette sampling, one raster at a time and distributed centisecond timing; palette controls now reach the encoder.

The export dialog includes MP4/WebM, frame rate, duration, resource issues, frame/phase progress and cancellation. Its format and scope controls have accessible names, initial keyboard focus enters the dialog and Tab navigation stays inside it. Downloads check the response before announcing success. The empty start screen says Ready. The 0.2.3 export-set implementation below replaces per-file batch publication; exact package and native acceptance are separately bound to executable hashes.

## 0.2.3 coherent export sets

`POST /api/docs/:id/export-set` takes `format`, `scales`, `artboards`/`artboard`, `comps`/`comp`, the existing format options, and `destination: "server" | "download"`. Supply both `expectedRev` and `expectedResources` from the reviewed preflight. One document copy and one resource capture cover every scale/target. Edits or external source changes after capture cannot change later members. A stale initial revision/hash refuses with 409. Target ids, ambiguous names, empty batches, numeric options, filename limits and case-insensitive sanitized-name collisions are validated before rendering. Existing destination files are hashed and checked again before replacement, including equal-size/timestamp mutations.

The MCP `export_set` tool exposes the same transaction for server-side exports. It requires reviewed revision/resource guards, typed scales, and explicit optional artboard/comp selections; its JSON result contains actual paths, dimensions and member hashes. The existing `export_document` tool remains available.

The dialog sends one request for multi-file Download and Save to server exports. For PDF artboard scope it produces one PDF per scale, with one page per artboard, rather than repeating the PDF for each target. Legacy `POST .../export` single and artboard/comp exports use the same transaction while retaining path/files response shapes, batch labels and absolute legacy URLs. Direct single-file GET downloads and project packages remain available. PNG, PNG-8, JPEG (jpg/jpeg), WebP, AVIF, GIF, TIFF (tif/tiff), BMP, PDF, SVG, layered PSD, HTML, MP4 and WebM remain supported. Non-raster artboard targets are cropped document copies, including timeline positions, rather than silently exporting PNG or repeating the whole canvas. PSD/SVG/HTML retain scale 1. MP4/WebM remain opaque whole-canvas video and refuse transparency/artboard requests. Existing GIF/video frame, work and odd-dimension limits still apply.

Every member is rendered with the production child renderer and staged in a private directory. Each child exits and all snapshot readers/copies retire before publication begins. Render, staging, cancellation and precommit failures leave the previous outputs intact. Publication replaces members sequentially and restores replaced members from verified backups on a handled failure; newly created members are removed on rollback. No completed file is exposed during rendering. Downloads return a bounded transient envelope only after all members render, their capture retires, and staging is removed. The binary envelope is a four-byte big-endian UTF-8 manifest length, JSON `{version:1, resourceSnapshot, files}`, then the ordered encoded member bytes. Each manifest member includes its actual filename, byte count, SHA-256, MIME and applicable dimensions/pages/video metadata. The dialog validates the complete envelope and member count before starting downloads, and retains individual clickable Blob links if browser automatic-download policy blocks later clicks.

The server admits two live sets. Each has at most 64 files; artboard PDFs have at most 64 pages each and at most 128 MiB of JPEG pages during assembly. Server staging **plus previous-file backups** is limited to 256 MiB per set and 512 MiB across live sets. Multi-download staging and its complete envelope are each limited to 128 MiB; manifests to 64 KiB. This is disk/encoded-byte accounting, not a claim that process RSS is 512 MiB: native canvases, IPC copies, a currently rendered encoded member, PDF assembly and a bounded download envelope also use memory. The existing 256 MiB encoded member, 16 MiB document, 64 MP/16384-side raster, and separate resource snapshot budgets remain. Reads of backups/envelope members are bounded even if files grow. Set work has a ten-minute cooperative deadline (504), disconnect/cancel is 499, and renderer watchdog/kill retirement still applies. Download-response admission and byte accounting persist until HTTP finish/close, with a 30-second response deadline. Browser Blob links retire on a new export, document/revision change, unmount or ten minutes.

An exclusive `.pictocity-export-set.lock` directory beside saved outputs excludes cooperating export writers across processes. It contains an owner marker, flushed recovery journal, staged members and backups. Concurrent sets targeting the same destination directory refuse with 409, even for disjoint filenames; use separate destinations for unrelated concurrent work. Locks are never stolen automatically. Directory identity/namespace and file hashes are guarded; external writers that ignore the lock are not made safe by it. Other server data operations still require one server per data directory. File renames do **not** make a set atomic to concurrent readers or Windows power loss: readers can observe sequential replacements during commit; a process/OS crash can leave a partial set and a retained lock. There is no automatic restart recovery or directory-fsync durability guarantee. Inspect the journal, old/new hashes and retained backups before manual recovery; do not delete a foreign/stale lock on assumption.

Incomplete rollback reports `committed:false`, `rollback.complete:false`, per-file diagnostics and actual retained recovery paths. Cleanup failure after commit reports `committed:true` and cannot return success. Failed transaction cleanup retains its admission/byte quota and lock; recovery is manual, and shutdown does not delete unresolved backups. Resource cleanup failures identify their retained directory/snapshot and retain the resource pool quota until a successful cleanup retry. No source or native evidence here establishes owner taste, listening, Adobe parity, package acceptance or delivery authority.

## Persistence and collaboration

Operation batches stage copies before publication; failed operations preserve state and revision, including optional properties. Locks protect groups and descendants. A flushed operation log precedes acknowledgment and recovers contiguous revisions after a process crash before snapshot. Partial tails are backed up and repaired; gaps block editing. Snapshot failures surface in health and retry. This is process-crash protection, not universal power-loss protection. Version 0.2.6 adds same-host physical data/docs ownership for cooperating servers; the older-version and external-writer limits above still apply.

Read-derived MCP convenience edits carry the fetched revision. Merge/image-processing tools expect their own asset-add revision before the final edit and refuse intervening changes. Those are separate transactions; a conflict can leave unused assets. Raw operations expose an optional caller guard. Interactive/offline editor reconciliation and collaborative undo still need dedicated work.
